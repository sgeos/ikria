# TP-0001, Green Monolith test procedure

> **Navigation**: [Verification](./README.md)

**Status.** Prepared on 2026-11-14. Steps 2 and 3 were done on 2026-11-15. Step 4 found
that a scan from the ground cannot cover Kerbin, and the test is paused there, as the
deferral of 2026-11-14 in `CAMPAIGN_SEQUENCE.md` allows. It resumes, with the design
below, when a vessel meets a Green Monolith. This is task T14 of [`V0_1_0.md`](../../docs/roadmap/V0_1_0.md).

**Purpose.** Establish how a Green Monolith chooses the node it grants, whether the pool
holds only nodes whose prerequisites are met, and the discovery distance. The reserved
set of [`CAMPAIGN_SEQUENCE.md`](../../docs/architecture/CAMPAIGN_SEQUENCE.md) depends on
all three.

**Save.** "Ikria Physical Verification" only, where the operator allowed debug features
on 2026-11-14. Every script runs `tools/phase0/guard.py` first and refuses any other
save. It identifies the loaded save by asking the game to write a uniquely named save,
since kRPC does not report which save is loaded.

**Method.** The operator's own, given on 2026-11-14. KerbNet scans a body from orbit and
marks each anomaly it detects with coordinates. Removing the sites the official wiki
lists, `record/sites/sites.json`, leaves the Green Monolith and the CommNet ground
stations, which KerbNet also shows. A discovery is recorded in the save as a world first
and a researched node, so each remaining candidate is checked by moving a probe to it
and reading the save.

## What happened at step 2

1. The first launch attempt, before step 2 existed, called `launch_vessel` for a craft
   whose parts the career had not researched. The call never returned.
2. After that, saving through kRPC still worked, but `load` and `quickload` both hung, and
   neither applied the edited file. The game ended in the state of its persistent save,
   with 10,000 funds and only the start node.
3. *Inference, now refuted.* The pattern fitted a modal dialog left open in the game
   window by the first launch.
4. On 2026-11-15 the operator reported that no dialog was open but kRPC's own settings
   window. Step 2 was repeated. The save and the edit completed, and `load` hung again
   until the script's 90-second limit. The game answered every later call, and a fresh
   save still held only the start node, so the load was not applied.
5. *Inference.* kRPC 0.7.0's `load` does not work from the Space Center in this setup.
   The cause is not known, and kRPC is not edited by this project.

**Resumed.** On 2026-11-15 the operator loaded the edited copy from the game's own Load
menu. A fresh save then held the start node and the nine nodes, so step 2 is done. The
edited copy is now named "ipv-edited", under the save names of
[`tools/phase0/README.md`](../../tools/phase0/README.md). Steps 4
and 5 are the operator's only other part, a single KerbNet session.

## Step 4, 2026-11-15

**From orbit, too narrow.** The operator opened KerbNet on the orbiting rover and found a
field of view of 10 degrees. The RoveMate core's part file, `probeRoverBody.cfg`, sets
`MaximumFoV = 10`, so a scan from orbit would take many orbits. The same file sets
`EnhancedMaximumFoV = 179.5` for the situations in `EnhancedSituationMask = 7`, which is
landed, splashed or before launch *(recall for the mask)*.

**From the ground.** `monolith_runway.py` launched a second rover onto the runway, at
latitude -0.05 and longitude -74.71 degrees, and saved the state as
"ipv-monolith-runway". The orbiting rover is left in place. A rover on the ground should
see about a hemisphere. The far side is to be seen from a second point near longitude
105 degrees, reached with the debug service's `set_landed`, at a point chosen clear of
every known site.

**The ground view is mostly static.** A screenshot of KerbNet at 179.5 degrees showed real
data only in a small patch near the rover, with one question-mark marker in it, and
static over the rest of the map. The marker lies 3.5 km from the known monolith near the
Space Center, within the map's resolution at that zoom *(inference)*. It was night, with
the Sun 70 degrees below the horizon, so the line warped to daylight, at a solar
elevation of 50 degrees, and saved "ipv-monolith-daylight". After a refresh the map was
unchanged, so darkness is not the limit. The cause of the static is not known.

**The rover rolled.** Between launch and the first screenshot it drifted about 1.5 km
east along the runway, to within about 1.6 km of the known monolith, before the line set
its brakes. No node was granted.

**What the window offers.** The window shows the coordinates of the point under the
mouse as "Target", to the arcminute, and a Waypoint button. kRPC reads waypoints with
their coordinates, so a marker made into a waypoint needs no copying by hand.

**No stock part scans widely and reliably.** From the game's part files:

**No position in the save.** The save holds a game seed but no monolith position.
Deriving the position from the seed would mean reverse engineering the game, which the
charter excludes. The localization dictionary holds 15 strings for "a VERY strange
monolith", which matches one Green Monolith on every body but Jool and the Sun
*(inference)*.

**No discovery yet.** Every save of steps 3 and 4 holds the same ten nodes.

## Search for a published method, 2026-11-15

**The operator's ruling.** The operator permitted a community method that gives a Green
Monolith's coordinates from the save's seed, for verification only, and ruled that using
one in the career would be cheating.

**Result.** No such method was found. *(web)*
- The wiki says Green Monoliths "do not have a fixed position, and will spawn randomly
  each game", and names no seed. The wiki's Green Monolith page and the forum thread
  refused automated access, so they were not read.
- A Steam discussion titled "Green Monolith Generation", of 2021, raises the seed
  question and leaves it unanswered. Players there report that a monolith "can move once
  spotted if you leave the SOI". *(hypothesis)* If so, its position is drawn when the
  body loads rather than fixed for the save, and a test must stay within one visit.
- A forum answer on the SCANsat mod reports that the game loads surface features only
  within about 6 to 7 km of the active vessel and does not store their positions.
  *(hypothesis)* That may explain the static of the ground view.
- SCANsat's anomaly scan finds anomalies from orbit. Whether it finds Green Monoliths
  was not established, and installing it would place it in the install the career
  shares.

## The design for resuming

The operator set out four hypotheses on 2026-11-15, G1 to G4 of
[`CAMPAIGN_SEQUENCE.md`](../../docs/architecture/CAMPAIGN_SEQUENCE.md). Placement at
random on entering the sphere of influence, a reward drawn at random at discovery, a
reward chosen by rule, and a reward drawn with the monolith that research might snipe.
When a verification or sandbox vessel next meets a Green Monolith, steps 5 and 6 above
are replaced by these.

**A replayed draw.** The operator noted on 2026-11-15 that if the state of the game's
pseudorandom number generator persists in the save, reloading one quicksave replays the
same draw. A random reward would then look fixed. The save holds `Seed` and `ROCSeed` at
its top level, and `GameSeed` and `ROCMissionSeed` in its ROC scenario *(files)*. Which of
them, if any, feeds the reward is not known. Each discovery below starts from the same
quicksave and changes one input, so that a change of reward can be traced to it.

1. **The quicksave.** Quicksave inside the sphere of influence, before the discovery, and
   copy the file aside.
2. **Plain reloads.** Reload and discover, three times in one game session. A different
   node across these means the draw uses state the save does not restore, which
   supports G2.
3. **Restarts.** Quit the game, start it, load the copy and discover, twice. A change here
   but not in step 2 means state held in memory across loads.
4. **Elapsed time.** From the copy, warp a different interval before each discovery, three
   times. A change here means the draw depends on game time or on draws made while time
   passes.
5. **The seeds.** Edit one seed at a time in further copies, loaded by the operator from
   the game's menu, and discover. A change traced to one seed means the reward derives
   from it.
6. **The snipe.** From the copy, research the node first granted and discover. Nothing
   granted, or the same node again, supports G4 and shows its outcome. A different node
   shows a draw from the remaining pool.
7. **Placement.** Leave the sphere of influence, return, and scan again. A different
   position supports G1. The same position may still be a seeded placement, so this
   step is also repeated after a seed edit.
8. **The distance.** Record the vessel's distance from the monolith at the discovery.

**Reading the results.** If the node never changes through steps 2 to 5, the reward is
fixed by rule, G3, or drawn at placement from an input not varied, G4, and step 6
separates the two. Any change in steps 2 to 5 favours G2, with the step naming the
input.
